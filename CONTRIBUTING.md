# Как работать с репозиторием

## Ветки и задачи

`main` содержит согласованную версию проекта, `develop` — изменения после ревью, `test` — состояние для проверки перед выпуском. Новую задачу берут из [бэклога](docs/backlog.md) и создают короткую ветку от `develop`: `feature/<название>`, `fix/<название>` или `docs/<название>`. Название пишут латиницей в нижнем регистре, слова разделяют дефисами.

Коммиты делают небольшими и содержательными. Сообщение на русском в формате Conventional Commits: `тип(область): что изменено` или `тип: что изменено`. Используют типы `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ci`. Например: `docs: уточнены критерии приёмки`. Если причина изменения неочевидна, её кратко объясняют в теле коммита.

## Pull request и ревью

1. Перед открытием PR запускают `npm run lint`, `npm run format:check` и `npm run build`.
2. PR направляют в `develop`. В шаблоне указывают задачу, связанное требование, что изменено и как это проверить.
3. Другой участник команды проверяет соответствие требованию, понятность кода или текста, результаты проверок и отсутствие секретов. Для слияния нужно минимум одно одобрение и закрытие обсуждений.
4. Автор исправляет замечания в той же ветке; при разногласиях команда обсуждает решение до слияния. К очередному занятию все участники должны быть согласны с изменениями.
5. После зелёных проверок и ревью PR сливают в `develop` через **Squash and merge**. Ветка PR удаляется после слияния.

Перед выпуском `test` синхронизируют с `develop`, проверяют результат и открывают PR из `test` в `main`. Выпуск сливают **merge-коммитом**, сохраняя историю изменений. Для `main` и `develop` включают защиту: запрет прямого push, force push и удаления, обязательное одобрение, успешный статус `quality` и актуальность ветки относительно целевой. Настройки защиты применяет владелец репозитория на GitHub.

## Проверки

Сейчас GitHub Actions на каждом PR в `develop` или `main` выполняет ESLint, проверку Prettier и сборку фронтенда. Эти проверки подтверждают качество каркаса, но не наличие бизнес-функций.

Когда появится логика приложения, для расчётов планируются unit-тесты на Vitest, для API — интеграционные тесты после выбора серверного стека, для основных пользовательских сценариев — Playwright. Инструменты и пороги покрытия будут уточнены вместе с соответствующими задачами.
