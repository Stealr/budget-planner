# Спецификация требований к «СтудБюджет»

## 1 Идея проекта и проблема

### 1.1 Идея проекта

Простой веб-сервис учёта личных финансов для студентов: доходы и расходы с карт и наличных в одном месте, месячные лимиты по категориям с предупреждениями и цели накопления. Без подключения к банку, без рекламы, бесплатно.

### 1.2 Проблема

- Половина людей вообще не ведёт учёт или ведёт его «в уме». По опросу ЮMoney (апрель 2025) [1](https://finance.mail.ru/article/rossiyane-rasskazali-ob-uchete-dohodov-i-rashodov-65757478/): учёт доходов и расходов ведут 53%, ещё 29% не считают совсем. Из тех, кто считает, 43% делают это в уме, 15% – в блокноте, 8% – в Excel, и только 6% – в специальных финансовых приложениях.
- Ситуация ухудшается. По данным SuperJob (август 2026) [2](https://snob.ru/news/issledovanie-u-39-rossiian-net-finansovoi-podushki/): 33% не ведут учёт доходов и расходов, 39% не имеют накоплений вообще, а высоко оценивают свою финансовую грамотность только 16% (год назад 26%).
- У молодёжи финансовая самостоятельность низкая. Исследование НИУ ВШЭ (2026) [3](https://naked-science.ru/article/column/molodye-rossiyane-znayut) среди школьников и студентов 15-19 лет из крупных городов: средний индекс финансовой автономии – 3,8 из 9.
- Почему студентам особенно тяжело: первые самостоятельные деньги; нерегулярные доходы (стипендия, подработка, помощь родителей); деньги разбросаны по нескольким картам и наличным. В итоге «до стипендии» денег не хватает.
- Почему существующие решения не помогают: приложения банков видят только свою карту. Специализированные приложения либо платные, либо сложные для новичка. Тетрадь и Excel неудобны с телефона и ничего не напоминают.

Формулировка проблемы: студенты не видят, куда уходят деньги, потому что доходы нерегулярные и разбросаны по картам и наличным, а удобного бесплатного инструмента «под студента» нет.

## 3 Анализ рынка и конкурентов

### 3.1 Способы учёта личных финансов

| Способ | Доля |
| --- | --- |
| В уме | 43% |
| Банковские приложения | 24% |
| Блокнот или тетрадь | 15% |
| Таблицы Excel | 8% |
| Специальные финансовые приложения | 6% |

Вывод: рынок приложений для учёта финансов есть, но им пользуется мало людей. Большинство считают в уме или на бумаге. Это и есть ниша: сделать так же просто, как тетрадь, но с подсказками и напоминаниями.

| --- | --- | --- |

| Дзен-мани | Синхронизация с банками, подробная аналитика | Бесплатная версия сильно ограничена, сложно новичку, синхронизация иногда сбоит |

Характеристики конкурентов приведены по обзору [5](https://finance.mail.ru/article/top-5-besplatnyh-prilozhenij-dlya-ucheta-dohodov-65030454/).

### 3.3 Gap – чем «СтудБюджет» отличается

1. Бесплатно и без рекламы – для студента платная подписка – аргумент не начинать.

2. Все деньги в одном месте: карты разных банков и наличные, без подключения к банку (а значит, без рисков с доступом к счетам).

3. Под студенческий цикл: шаблон бюджета «от стипендии до стипендии», регулярные траты (общежитие, проезд, подписки).

4. Максимально просто: добавить трату – за 3 действия.

5. Веб-приложение: работает с телефона и компьютера без установки.

### 3.4 Временные рамки (оценка)

| Вопрос | Ответ |
| --- | --- |
| Что успеем за семестр | Рабочий веб-прототип (MVP) с учётом операций, лимитами, дашбордом и целями – к 18.12.2026 |
| Сколько заняла бы полная реализация | ≈ 6–9 месяцев: мобильные приложения, импорт выписок, совместный бюджет, обучающие материалы |
| Как долго продукт был бы конкурентоспособен | 2–3 года при развитии; основной риск – банки добавят похожие функции «для всех карт» |

## 4 Стратегическое видение

Структура стратегического видения построена по схеме «миссия – видение – направления – цели – задачи»

| Уровень | Формулировка |
| --- | --- |
| Миссия | Сделать управление деньгами простой привычкой для студентов, чтобы с первой стипендии они жили по плану, а не «до следующей выплаты». |
| Видение | Молодые люди с первых самостоятельных денег понимают, куда они уходят, умеют откладывать и не боятся конца месяца. Барьеры: привычка считать «в уме», лень вносить траты, недоверие к финансовым сервисам. Преимущество: простота и отсутствие доступа к банку. |
| Ценности | Простота · приватность (никаких доступов к банку) · честность (бесплатно, без рекламы) · польза с первого дня |
| Направления (Strategic Themes) | 1) снизить порог входа в учёт финансов; 2) сделать учёт регулярным (напоминания, лимиты); 3) помочь копить (цели) |
| Цель (Goal) | Выпустить рабочий прототип, которым реально пользуются студенты из тестовой группы (см. подраздел 5.1) |

Миссия команды как разработчиков: сделать полезный и честный инструмент, который мы сами хотели бы использовать, и научиться при этом полному циклу разработки – от требований до CI.

Обоснование ценности проекта: тема социально значимая (финансовая грамотность – национальный приоритет, см. программы Банка России), у проблемы есть свежие цифры, а объём реалистичен: к декабрю будет работающий продукт, а не презентация.

## 5 SMART-цель, стратегические задачи и метрики

### 5.1 SMART-цель (для прототипа)

До 18 декабря 2026 года команда из 3 человек выпустит веб-прототип «СтудБюджет», в котором студент может зарегистрироваться, вести доходы и расходы, задать месячные лимиты по категориям и видеть отчёт по тратам. Прототип запускается одной командой (docker compose up), все требования категории Must проходят критерии приёмки, а не менее 5 студентов из тестовой группы пользуются им 2 недели.

| Критерий | Как выполнен |
| --- | --- |
| S – Specific | Конкретный продукт (веб-прототип) и конкретный набор функций: регистрация, операции, лимиты, отчёт |
| M – Measurable | 100% Must-требований приняты; ≥ 5 тестовых пользователей; 2 недели использования; запуск одной командой |
| A – Attainable | Небольшой объём (4–5 сущностей в БД), без интеграций; в команде есть фронтендер с опытом; остальное – по плану практик |
| R – Relevant | Цель отвечает миссии (простой учёт для студентов) и задачам курса (React, Node.js, Docker, Git, тесты, CI) |
| T – Time-bound | Срок – 18.12.2026 (ПР8, итоговая презентация); промежуточные точки – по плану практик |

## 6 Команда и роли

Роли этапа анализа определены по модели жизненного цикла разработки ПО. В команде три человека, поэтому один участник совмещает две роли.

| Участник | Роль на этапе анализа | Позиция в дебатах о требованиях | Роль в разработке |
| --- | --- | --- | --- |
| Михаил | Product Owner + Project Manager | За заказчика/пользователя: «студенту нужно вот это» | Фронтенд (React), архитектура фронта |
| Дмитрий | CTO (технический лидер) | За ограничения: «за 2 месяца втроём это не успеем, режем» | Бэкенд (Node.js), БД, Docker |
| Анвар | Business Analyst | Документирование: фиксирует решения, ведёт SRS и матрицу | Справочники, валидация, unit-тесты расчётов, документация |

Организация работы над практикой: общение шло в общем чате команды. Сначала была выбрана тема и распределены роли, затем обсудили проблему, аудиторию и конкурентов, 3 этапом согласовали требования и приоритеты. Все материалы собирались в общем Google документе, разделённом по разделам отчёта. Каждый участник заполнял свои разделы. Задачи по подготовке практики велись на доске GitHub Projects с колонками «Бэклог», «В работе», «Ревью» и «Готово».

В ходе обсуждений возникли два разногласия. Первое касалось интеграции с банками: Product Owner предлагал автоматически загружать операции из банковских приложений, чтобы пользователю не приходилось вносить траты вручную. CTO возразил, что интеграция с банками требует доступа к банковским данным, договорённостей с банками и не укладывается в срок до декабря. После обсуждения функцию отнесли к категории Won't have, а проблему ручного ввода решили через быстрое добавление операции

## 7 Модель и методология разработки

Выбор сделан на основе сравнения моделей и методологий разработки

Модель: итеративно-инкрементная (эволюционная). Каждые 1–2 недели новый рабочий инкремент, привязанный к практикам; требования уточняются

Методология: Kanban с элементами Scrum.

- Kanban-доска в GitHub Projects: колонки «Бэклог - К работе - В работе - Ревью - Готово», лимит WIP – 2 задачи на человека.
- Из Scrum: короткая еженедельная встреча (план на неделю + ретроспектива), бэклог продукта с приоритетами, демонстрация на каждой практике (аналог обзора спринта)

### 8.3 Сценарий использования (Use Case) – «Добавить расход»

Сценарий описан по шаблону Use Case

| --- | --- |
| Актор | Студент |

## 9 Спецификация требований (SRS, версия 1.0)

Требования разделены по уровням в соответствии с практикой IEEE: бизнес-требования, пользовательские, функциональные и нефункциональные требования

### 9.1 Бизнес-требования (БТ)

| ID | Требование |
| --- | --- |
| БТ-1 | Пользователь видит все свои доходы и расходы в одном месте |
| БТ-2 | Пользователь может планировать траты на месяц и контролировать их |
| БТ-3 | Пользователь может копить на цели |
| БТ-4 | Учёт должен быть регулярным и требовать минимум усилий |
| БТ-5 | Данные пользователя защищены и доступны только ему |

### 9.2 Функциональные требования (ФТ) с критериями приёмки

| ID | Требование | Критерии приёмки | Приоритет |
| --- | --- | --- | --- |
| ФТ-1 | Регистрация и вход по email и паролю | Регистрация с валидным email и паролем ≥ 8 символов создаёт аккаунт; повторный email → ошибка «Email уже занят»; неверный пароль → «Неверный email или пароль»; после входа видны только свои данные | Must |
| ФТ-2 | Добавление операции: тип (доход/расход), сумма, категория, дата, источник (карта/наличные), комментарий | Сохраняется операция с суммой > 0; дата по умолчанию – сегодня; операция сразу появляется в списке и меняет баланс | Must |
| ФТ-3 | Редактирование и удаление операции | Изменённая сумма пересчитывает баланс; удалённая операция пропадает из списка и отчётов; удаление требует подтверждения | Must |
| ФТ-4 | Категории: стандартный набор + свои | Новый пользователь сразу видит 8–10 стандартных категорий (еда, транспорт, общежитие/жильё, связь, развлечения, учёба, одежда, подписки, другое); можно создать, переименовать и архивировать свою | Must |
| ФТ-5 | Список операций с фильтрами (период, тип, категория, источник) | Фильтр «октябрь + еда» показывает только операции еды за октябрь; сумма по фильтру отображается | Must |
| ФТ-6 | Месячные лимиты по категориям | Можно задать лимит в ₽ для категории на текущий месяц; виден прогресс «потрачено X из Y» | Must |
| ФТ-7 | Дашборд: баланс, расходы по категориям (круговая диаграмма), динамика по дням/неделям | Сумма секторов диаграммы = сумме расходов за период; данные совпадают со списком операций | Must |
| ФТ-8 | Предупреждения о лимитах | При ≥ 80% лимита – жёлтое предупреждение; при > 100% – красное; видно на дашборде и после добавления операции | Should |
| ФТ-9 | Цели накопления: название, сумма, срок, пополнение, прогресс | Пополнение цели увеличивает прогресс и не считается расходом; при достижении суммы цель помечается выполненной | Should |
| ФТ-10 | Регулярные платежи (общежитие, проезд, подписки) | Можно задать сумму, категорию и день месяца; за 3 дня до даты – напоминание в интерфейсе; одним нажатием создаётся операция | Should |
| ФТ-11 | Экспорт операций в CSV | Файл открывается в Excel, содержит все операции за выбранный период | Could |
| ФТ-12 | Шаблон бюджета «от стипендии до стипендии» | При выборе шаблона лимиты распределяются по категориям в процентах от указанного дохода | Could |
