## Данные и состояние

- **RTK Query** ведёт кеш операций и категорий. После создания, изменения или удаления операции инвалидируем теги `Transactions`, `Dashboard` и `Limits`. После изменения, архивирования или удаления категории обновляются также `Categories` и связанные подписи в истории, лимитах и сводке.
- **Лимиты** кешируются отдельно для каждого месяца. Сохранение и удаление лимита обновляют `Limits` и `Dashboard`. Фактические расходы берутся из серверного `spentAmount`, независимо от страницы истории.
- **Redux-слайсы** хранят состояние сессии и мобильного меню. Запросы регистрации и входа используют отдельный `fetch`: пароль не попадает в Redux, его действия и кеш RTK Query.
- **Формы** хранят поля, включая пароль, локально. В `sessionStorage` сохраняются только `accessToken`, `tokenType`, `expiresAt`.
- **URL** хранит период истории, тип, категорию и страницу. Фильтры применяются кнопкой; смена условий сбрасывает страницу, обновление страницы и переход «Назад» сохраняют выбранные условия. Архив категорий переключается параметром `includeArchived=true`.

## Авторизация

`/login` и `/register` доступны без входа; остальные маршруты защищены. Регистрация создаёт аккаунт, затем открывает вход с заполненным email. Пароль регистрации — от 8 символов до 72 байт UTF-8, без нулевого символа. Пробелы в пароле сохраняются.

После входа пользователь возвращается на исходную внутреннюю страницу вместе с параметрами и якорем. Сессия восстанавливается синхронно до запросов защищённых страниц. Токен непрозрачный, API получает его как `Authorization: Bearer …`.

Сессия действует в пределах вкладки и переживает обновление страницы. Если браузер запретил `sessionStorage`, она сохраняется только до перезагрузки. При истечении `expiresAt`, ответе `401` защищённого API или нажатии «Выйти» сессия и кеш очищаются, активные запросы отменяются. Запоздалый ответ предыдущего аккаунта не может заполнить кеш нового или завершить его сессию. `401` при неверном пароле остаётся ошибкой формы входа.

На сервере нет refresh и logout: после истечения требуется повторный вход, а выход очищает клиентскую сессию без отзыва токена на сервере.

## Проверки

- **Vitest** проверяет восстановление сессии, безопасный адрес возврата, границы денежных сумм и валидацию периода и фильтров.
- **React Testing Library и MSW** проверяют авторизацию, формы и CRUD операций и категорий, архив, конфликты, фильтры, пагинацию и обновление связанных данных.
- **axe-core** проверяет доступность форм. Проверка контраста и реальной адаптивной вёрстки выполняется в браузере.

Из корня: `npm test`; для наблюдения за тестами — `npm exec --workspace frontend -- vitest`.
CI выполняет `npm run lint`, `npm run format:check`, `npm run build`, `npm test`.

## Текущие возможности

Работают регистрация и вход, доходы и расходы с редактированием и подтверждением удаления, фильтры истории по периоду, типу и категории, создание и изменение собственных категорий, их архивирование и удаление, месячные лимиты и предупреждения после добавления расхода. На мобильном экране операции отображаются карточками. Дашборд и настройки пока открывают экраны каркаса.

Стандартные категории защищены от изменения. Новая операция использует активную категорию своего типа; при редактировании можно сохранить прежнюю архивную категорию. История берёт `categoryName` из ответа операции и не зависит от активного справочника. Категория со связанными операциями или лимитами не удаляется: интерфейс предлагает архивирование. Смена типа такой категории также может быть отклонена; форма сохраняет введённые данные и объясняет конфликт.

Суммы операций вводятся в рублях от `0,01` до `999 999 999,99`, с точкой или запятой и не более чем двумя знаками после разделителя. История сортируется по дате и затем по ID, от новых к старым; после удаления последней записи страницы выбирается существующая страница.

API пока не хранит источник «карта/наличные» и не возвращает общий денежный итог по всем фильтрам; соответствующие поля и итог не имитируются клиентом. Кнопка импорта скрыта до появления серверного API; прямой маршрут импорта остаётся заглушкой.

## Лимиты и предупреждения

В `/limits` по умолчанию выбран текущий месяц. Параметр URL `month=YYYY-MM` сохраняет другой месяц; при переключении данные предыдущего месяца не показываются под новым заголовком. Некорректный месяц не отправляется в API. Для каждой категории показаны серверные расходы, лимит, остаток либо превышение и процент. Полоса прогресса ограничена 100%, текст показывает фактический процент.

Лимит создаётся или обновляется через `PUT /api/v1/limits/{categoryId}?month=…`, удаляется с подтверждением через `DELETE`. В форме доступны только активные категории расходов. Если лимит уже существует, новая настройка заменяет его сумму, о чём форма предупреждает. Лимит архивной категории можно просматривать и удалять. Как и для операций, ввод в текущем интерфейсе ограничен `0,01…999 999 999,99 ₽`: расширение до 17 целых цифр серверного DTO требует отдельного согласования точности.

После успешного создания расхода интерфейс показывает `limitWarning` из ответа POST вне закрывшейся формы. В уведомлении указаны категория и календарный месяц операции, включая расход задним числом. Ниже 80% предупреждения нет, 80–100% включительно — жёлтый `NEAR_LIMIT`, строго выше 100% — красный `EXCEEDED`. Цвет берётся из серверного `level`, а не из округлённого процента. Доходы и редактирование операции не создают такое уведомление; правка и удаление обновляют прогресс через кеш. На дашборде предупреждения будут подключены следующим этапом.

Общий модуль RTK Query находится в `src/store/api.ts`. По умолчанию он использует `/api` на том же домене. Для отдельного адреса API задайте `VITE_API_BASE_URL` при запуске Vite. Эндпоинты подключены через `api.injectEndpoints` в `src/transactions/api.ts`, `src/categories/api.ts` и `src/limits/api.ts`. Авторизация находится в `src/auth/`.

## Запуск сценария добавления расхода

Для запуска всего приложения выполните из корня `docker compose up -d --build --wait` и откройте [«Операции»](http://localhost:8080/transactions). Сначала зарегистрируйтесь и войдите.

Для локальной разработки понадобятся Docker, JDK 21 и Node.js 24+. В отдельных терминалах запустите PostgreSQL, Spring Boot и Vite:

```powershell
# Из корня репозитория
docker compose -f backend/docker-compose.yml up -d --wait postgres
```

```powershell
Set-Location backend
.\gradlew.bat bootRun
```

```powershell
# Из корня репозитория
npm ci
npm run dev
```

Vite проксирует запросы `/api` на `http://127.0.0.1:8080`. При размещении фронтенда отдельно задайте `VITE_API_BASE_URL` с путём `/api` и настройте доступ к API.

Миграция создаёт десять стандартных категорий. Создавать категорию вручную для первого расхода не требуется. Прямые запросы к API вне фронтенда требуют заголовок `Authorization: Bearer <accessToken>` после `POST /api/v1/auth/login`; контракт описан в [README бэкенда](../backend/README.md).

1. Зарегистрируйтесь, войдите, откройте раздел «Операции» и нажмите «Добавить операцию».
2. Оставьте тип «Расход», введите `450,50`, выберите стандартную категорию расхода, оставьте сегодняшнюю дату и сохраните. Записи сортируются по дате операции, затем по ID.
3. Перезагрузите страницу и проверьте, что запись осталась в списке.
4. Измените сумму и комментарий через кнопку редактирования строки. Удаление сначала отмените, затем подтвердите: запись должна исчезнуть.
5. Создайте доход, выбрав тип «Доход» и категорию доходов. Примените период, тип и категорию фильтра; обновите страницу и проверьте условия в URL.
6. Создайте собственную категорию, переименуйте её и добавьте операцию с ней. Попытка удаления категории должна предложить архивирование. После архивации название сохраняется в истории, прежняя операция редактируется, но новая операция архивную категорию не предлагает.
7. Выйдите и войдите другим аккаунтом: собственные категории и операции первого аккаунта не должны показываться.
8. В «Лимитах» выберите месяц и задайте лимит активной категории расходов. Добавьте расходы, достигающие 79%, 80%, 100% и более 100%: проверьте прогресс и предупреждение после сохранения. Для расхода задним числом предупреждение должно относиться к его месяцу.
9. Измените сумму расхода или удалите его, вернитесь к лимитам: серверный прогресс должен обновиться. Измените или удалите лимит; при удалении операции должны сохраниться. Проверьте также лимит архивной категории.
