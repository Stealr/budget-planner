# Бэкенд

REST API операций и категорий на Java 21 и Spring Boot. PostgreSQL хранит данные, Liquibase управляет миграциями.

Для запуска всех сервисов используйте [Compose из корня репозитория](../README.md#запуск-в-docker).

Для разработки бэкенда отдельно можно поднять только PostgreSQL и запустить Spring Boot с локальным JDK 21. Выполните из каталога `backend`:

```powershell
docker compose up -d --wait postgres
.\gradlew.bat bootRun
```

В этом режиме PostgreSQL доступен на порту `5433`, API — на порту `8080`.

## Регистрация и вход

Передавайте JSON с полями `email` и `password` в `POST /api/v1/auth/register`.
Успешная регистрация возвращает `201` и поля `id` и `email`. Занятый email
возвращает `409`. Email приводится к нижнему регистру. Пароль должен содержать
минимум 8 символов и занимать не более 72 байт в UTF-8.

`POST /api/v1/auth/login` принимает те же поля и возвращает `200` с
`accessToken`, `tokenType` и `expiresAt`. Токен действителен 24 часа по умолчанию. Срок можно задать через `APP_AUTH_ACCESS_TOKEN_TTL` (например, `PT2H`). В БД хранится SHA-256 токена. Просроченные токены удаляются раз в час. Интервал задаётся через `APP_AUTH_CLEANUP_INTERVAL`.
При неверном email или пароле API возвращает `401` с общим сообщением.

Передавайте `Authorization: Bearer <accessToken>` в запросах к категориям
операциям и лимитам. В Swagger UI вставьте токен через **Authorize**. Списки содержат
стандартный каталог и категории текущего аккаунта. Операции и лимиты видны только владельцу. Запросы к чужим записям по ID возвращают `404`.

Миграция сохраняет существующие категории и операции без владельца.
Они не видны через API аккаунтов. Для переноса таких данных нужно явно
назначить владельца категориям, операциям и лимитам.

## Категории

Liquibase добавляет десять стандартных категорий. Поле `standard` отличает
каталог от созданных пользователем категорий. Стандартные категории защищены
от переименования, удаления и архивирования.

- `GET /api/v1/categories` возвращает активные категории.
- `GET /api/v1/categories?includeArchived=true` включает архив. Поле
  `archivedAt` содержит дату архивации или `null`.
- `PATCH /api/v1/categories/{id}/archive` архивирует пользовательскую
  категорию и возвращает `204`. Повторный вызов сохраняет дату архивирования.
- `DELETE /api/v1/categories/{id}` удаляет пользовательскую категорию без
  связанных операций и лимитов. При наличии связей API возвращает `409`.

Новые операции и перенос операций в архивную категорию отклоняются с `409`.
Исторические операции доступны для чтения и редактирования с прежней
категорией. Ответ операции содержит `categoryName` для отображения истории.

## Месячные лимиты

Месяц передаётся как `YYYY-MM`. Лимит задаётся в рублях для активной
категории расходов. На аккаунт, категорию и месяц приходится одна запись.

- `PUT /api/v1/limits/{categoryId}?month=2026-11` создаёт или обновляет
  лимит. Тело запроса — `{"amount": 5000.00}`.
- `GET /api/v1/limits?month=2026-11` возвращает все лимиты месяца.
- `GET /api/v1/limits/{categoryId}?month=2026-11` возвращает один лимит.
- `DELETE /api/v1/limits/{categoryId}?month=2026-11` удаляет лимит.

Ответ содержит `limitAmount` и `spentAmount`. Расходы считаются по датам
операций с первого дня месяца до первого дня следующего месяца. При
архивировании категории существующие лимиты остаются доступны для просмотра
и удаления.

## Данные дашборда

`GET /api/v1/dashboard?dateFrom=2026-11-01&dateTo=2026-11-30&groupBy=WEEK`
требует Bearer-токен. Обе даты обязательны и включаются в период. Параметр
`groupBy` принимает `DAY` (по умолчанию) или `WEEK`.

- `openingBalance` — баланс до начала периода, `balance` — баланс на конец
  выбранного периода. `income` и `expenses` — суммы за выбранные даты.
- `expensesByCategory` — суммы расходов по категориям, включая архивные
  категории с операциями за период.
- `trend` — точки с доходами и расходами. Для недель `periodStart` указывает
  понедельник. В неполные недели входят только выбранные даты. Дни и недели
  без операций отсутствуют в массиве.

Все суммы возвращаются в рублях. Для пустого периода доходы и расходы
равны нулю; баланс равен остатку на начало периода.

## Предупреждения о лимитах

Если расходы достигли 80% лимита и не превысили его, API возвращает
`NEAR_LIMIT` (жёлтое предупреждение). При расходах строго больше лимита
возвращается `EXCEEDED` (красное). Порог проверяется по точным суммам.
Поле `usagePercent` округляется до двух десятичных знаков.

После добавления расхода `POST /api/v1/transactions` возвращает
`limitWarning`, если сработал порог для категории и месяца операции.
Доходы и расходы без сработавшего предупреждения возвращаются без этого поля.

`GET /api/v1/dashboard` возвращает `limitWarnings` за календарные месяцы,
которые пересекаются с выбранным периодом. Предупреждение учитывает расходы
за весь соответствующий месяц даже при выборе отдельных дней. Если порог
не достигнут ни по одному лимиту, массив пуст.

## Цели накопления

- `POST /api/v1/goals` создаёт цель. Пример тела запроса — `{"name":"Ноутбук","targetAmount":60000,"dueDate":"2027-03-01"}`.
- `GET /api/v1/goals` возвращает цели аккаунта, а `GET /api/v1/goals/{goalId}` — одну цель и её прогресс.
- `PUT /api/v1/goals/{goalId}/contributions/{requestId}` пополняет цель. Тело — `{"amount":5000}`. Для каждого пополнения клиент создаёт UUID и повторно использует его, если нужно повторить запрос. Тот же UUID и сумма возвращают текущий прогресс без повторного пополнения. Повтор UUID с другой суммой возвращает `409`.

Дата пополнения определяется сервером в UTC. Цель считается выполненной,
когда `savedAmount` достигает `targetAmount`. Пополнения учитываются отдельно
от доходов и расходов. В дашборде `reservedForGoals` — сумма пополнений по
дату окончания периода включительно. `availableBalance` — общий баланс за
вычетом этой суммы.

## Регулярные платежи

`POST /api/v1/recurring-payments` создаёт платёж, `GET` возвращает платежи
аккаунта, `PUT /api/v1/recurring-payments/{paymentId}` обновляет настройки,
а `DELETE` удаляет настройку с сохранением проведённых операций.
Пример тела POST и PUT:

```json
{"name":"Общежитие","amount":3500,"categoryId":3,"dayOfMonth":31,"remindersEnabled":true}
```

Для платежа нужна активная категория расходов. Если в месяце нет заданного
числа, срок переносится на последний день месяца.

`GET /api/v1/recurring-payments/reminders` возвращает неподтверждённые
платежи с включёнными напоминаниями, срок которых наступает сегодня или
в ближайшие три календарных дня. Даты считаются в UTC. Для показа при входе
или открытии приложения фронтенд должен запросить этот список.

`PUT /api/v1/recurring-payments/{paymentId}/occurrences/{dueDate}/confirm`
подтверждает платёж в этом окне и создаёт расход датой подтверждения.
Дата срока передаётся в формате `YYYY-MM-DD`. Повтор запроса не создаёт
второй расход. Если созданный расход впоследствии удалён, повтор вернёт
`transactionId: null`. Платёж с выключенными напоминаниями можно
подтвердить вручную в те же даты.
